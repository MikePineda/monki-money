# API contract

The contract between `apps/api` and `apps/web` is the **Tuyau registry**
generated from the API routes (`apps/api/.adonisjs/client/registry`), plus the
types in `@monkimoney/shared`. There is no hand-written OpenAPI file and no
mock server.

## How it works

1. Every route has a name (`.as('group.resource.action')`) and a controller
   whose return type is the response body.
2. `npm run codegen` regenerates `apps/api/.adonisjs` (also done by
   `node ace build` and `node ace serve`). The folder is committed.
3. The web app imports the registry through tsconfig `paths`
   (`@monkimoney/api/registry`, `@monkimoney/api/data`) and creates the client
   in `apps/web/src/app/core/api.ts`.
4. Change a route or a response shape, run `npm run codegen`, and
   `npm run typecheck` fails in the web app wherever the old shape was used.
   CI runs codegen and fails on any diff in `apps/api/.adonisjs`.

The SPA fallback route (`spa.fallback`) is excluded from the registry
(`adonisrc.ts`).

## Conventions

- Business endpoints live under `/api/v1`; probes (`/api/health*`) do not.
- Success bodies are `{ data }`; paginated lists are `{ data, metadata }`
  with `perPage <= 100`.
- Validation errors: 422 `{ errors: [{ field, rule, message }] }`, localized.
  Service-level checks use the same shape (e.g. `email`/`alreadyMember`,
  `externalAccountNumber`/`taken`, a foreign id in the body →
  `<field>`/`database.exists`).
- Other 4xx: `{ message, code }` with the message translated
  (`resources/lang/<locale>/errors.json`), e.g. 404 `E_ROW_NOT_FOUND`,
  403 `E_EMAIL_NOT_VERIFIED` / `E_NO_HOUSEHOLD` / `E_HOUSEHOLD_PENDING_DELETION`
  / `E_HOUSEHOLD_SUSPENDED` / `E_BAD_CSRF_TOKEN` / `E_TRANSACTION_PRIVATE` (a
  partner's private transaction), 402 `E_MEMBER_LIMIT_REACHED`
  / `E_ACCOUNT_LIMIT_REACHED` / `E_LLM_QUOTA_EXCEEDED` (plan limits,
  `config/plans.ts`), 409
  `E_ACCOUNT_IN_USE` / `E_CATEGORY_IN_USE` / `E_GROUP_NOT_EMPTY` /
  `E_ALREADY_IN_HOUSEHOLD` / `E_TRANSFER_LEG` (edit the transfer, not its leg) /
  `E_PAYSLIP_LINE` (a payslip row's amount, kind, account, date or existence) /
  `E_CONFLICT` (a unique-constraint race; a foreign-key race answers
  `E_CATEGORY_IN_USE` / `E_ACCOUNT_IN_USE` when the delete lost it) /
  `E_CONCURRENT_UPDATE` (a deadlock or serialization failure: nothing was
  written, retry), 410
  `E_INVITATION_EXPIRED`, 400 `E_INVALID_TOKEN`, 422 `E_OWNER_CANNOT_LEAVE`. Bank imports add 422 `E_CSV_*`
  (`E_CSV_TOO_LARGE`, `E_CSV_TOO_MANY_ROWS`, `E_CSV_ENCODING`, `E_CSV_UNKNOWN_FORMAT`,
  `E_CSV_MALFORMED`, `E_CSV_INVALID_VALUE`, `E_CSV_EMPTY`; with `line` / `column`
  when known), 422 `E_IMPORT_UNKNOWN_ACCOUNTS` (`accountNumbers[]` to map),
  422 `E_IMPORT_ROWS_UNDECIDED` (`rowIds[]`), 409 `E_IMPORT_BATCH_OPEN`
  (`batchId`, `accountId`), 409 `E_IMPORT_BATCH_CLOSED`, 402
  `E_IMPORT_LIMIT_REACHED` and `E_LLM_QUOTA_EXCEEDED`; the fields in parentheses
  come next to `message` and `code`. Auth, throttle and role failures keep the framework
  shape `{ errors: [{ message }] }`: 400 bad credentials, 401 not logged in
  (or revoked session), 403 role (`HouseholdPolicy`), 429 throttled (with
  `Retry-After`).
- 5xx in production: a generic translated `{ message, code: 'E_INTERNAL_SERVER_ERROR' }`
  (driver, table and constraint names stay in the logs), except 503
  `E_INSIGHTS_UNAVAILABLE` (no LLM configured), `E_LLM_UNAVAILABLE` (the
  LLM vendor failed, or receipt scanning without a configured LLM) and
  `E_STORAGE_UNAVAILABLE` (no bucket, or it did not answer), which keep their
  translated `{ message, code }` in every environment ("try again later").
- Unknown routes: JSON 404 (`{ message, code }`), including any `/api/*` GET
  that would otherwise hit the SPA fallback.
- Amounts are integer cents named `*Cents`; dates are `YYYY-MM-DD` (years
  1900-2999, months `YYYY-MM` likewise; ids fit a Postgres `integer`, anything
  else is a 422); timestamps are ISO-8601 UTC strings. People send amounts positive
  (`amountCents > 0`) with a `kind`; the ledger returns them signed
  (expenses and outgoing transfer legs negative). Report amounts are
  positive on their own side (`expenseCents` = spent, net of refunds).
- Idempotent creates: `POST /transactions[/quick]` and `POST /transfers`
  accept a client-generated `clientId` (uuid). The first request answers
  201; a retry with the same key answers 200 with the row it created
  (unique per household, also under a race).
- Private transactions (`isPrivate`): only the payer (or, for a joint one,
  its creator; nobody once that owner is deleted or leaves the household,
  when the row becomes ordinary) sees `payee`, `description`, `rawDescription`, `tags`,
  `categoryId` and the split lines; the partner gets them empty with
  `isMasked: true` (and `needsReview: false`), never matches them in
  searches, category or review filters, sees the amount under the `private`
  bucket in reports, cannot change the row (403 `E_TRANSACTION_PRIVATE`) and
  bulk categorize, bulk tags and tag renames skip it.
- Another household's resource: 404, never 403.
- Leaving members (`household.leave`; the same rule applies to a removal by
  the owner if that route is ever added): in the same transaction that
  drops the membership, their personal accounts become joint
  (`ownerUserId: null`), their cards on any account of the household keep
  the suffix but lose their `userId`, and merchant rules, recurring items
  and import rows still to confirm (suggested payer and a decided payer)
  stop naming them as the payer. New rows on those accounts and cards then
  default to whoever enters them (`defaultPayer`) instead of someone who is
  gone. Existing ledger rows and confirmed import rows keep
  `paidByUserId` and `createdByUserId`: history is history. Leave, delete
  and ownership transfer decide on the locked, committed membership, so a
  handover racing a leave never leaves the household without an owner.
- Locale of messages: the user's `locale`, else `Accept-Language`, else the
  household's, else `APP_DEFAULT_LOCALE` (`en`). Responses carry
  `Content-Language`. System categories/groups (`isSystem`) are named in that
  locale; custom (or renamed) ones keep the typed name.

## Session and CSRF

Cookie session (`monkimoney_session`, httpOnly, `secure` in production,
`SameSite=Lax`, 30 days). Every request sets the `XSRF-TOKEN` cookie; every
POST/PUT/PATCH/DELETE must send it back as `X-XSRF-TOKEN` (Tuyau does it).
SPA boot: `GET /api/v1/auth/me` (401 for guests, but the cookie is set), then
`POST /api/v1/auth/login`. Login, logout-all, password change and password
reset bump `users.session_version`; sessions stamped with an older version
answer 401.

Middleware per group: public auth routes (throttled per IP, plus email where
there is one); _authenticated_ (`auth`, session version, 300 req/min per user:
`auth.me`, `auth.logout*`, `auth.email.resend`, `auth.email.verifyCode`,
`me.update`); _verified_ (authenticated + verified email, no household needed:
`households.store`); _household_
(authenticated, verified email and household context: everything under
`/household`, `/accounts`, `/category-groups`, `/categories`, `/transactions`,
`/transfers`, `/payslips`, `/reports`, `/tags`, `/goals`, `/insights`, `/recurring`).
`household.restore` is the only household route allowed while the household
is pending deletion.

Throttles (429): login, sign-up, forgot/reset password and invitation
lookups/accepts 5/min (then 20 min blocked) per client IP (+ email); password
re-checks (`PATCH /me` with `password`, `household.delete`,
`household.transferOwnership`; only wrong passwords count) 5/min per user;
`auth.email.resend` 3 per 15 min per user; wrong `auth.email.verifyCode`
codes 5/min (then 20 min blocked) per client IP + email; invitation mails (create + resend)
10/hour per household. The client IP is `CF-Connecting-IP` only when the
request came through the local proxy (see `docs/RUNBOOK.md`).

### Bot protection (Cloudflare Turnstile)

Off while `TURNSTILE_SECRET` is empty (the body field is ignored). With a
secret, `auth.signup`, `auth.login` and `auth.password.forgot` require
`turnstileToken` (the widget token; the site key comes from `GET /config`)
and check it with Cloudflare's siteverify (client IP from `clientIp(ctx)`,
5 s timeout, fails closed) before validation, credentials and throttles: a
missing or rejected token answers 422 `{ field: 'turnstileToken', rule:
'turnstile' }` and never counts toward the login/sign-up/forgot limits.
Enabling it: `docs/RUNBOOK.md` ("Turnstile").

Test-only (exist only with `NODE_ENV=test` or `E2E_MODE=true`, CSRF-exempt,
not in the registry): `POST /api/test/reset` (wipe the database, throttles and
outbox; seed the E2E household) and `GET /api/test/outbox` (mails the `log`
transport "sent" since the last reset, newest last, at most 50:
`{ data: [{ to, subject, links, codes, sentAt }] }`, `codes` = the 6-digit
verification codes in the body).

### Household export

`GET /household/export` is the owner's "download my data". Both formats
carry the same tables, rows and columns (`app/services/households/export_tables.ts`):

| JSON key             | CSV file                  | Rows                                                                                                                                                     |
| -------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `household`          | `household.csv`           | The household (one object; one row in the CSV)                                                                                                           |
| `members`            | `members.csv`             | Current members with name, email and role                                                                                                                |
| `accounts`           | `accounts.csv`            | Accounts with owner, account number and opening balance (cents and date)                                                                                 |
| `accountCards`       | `account_cards.csv`       | Cards by account (suffix, user, label)                                                                                                                   |
| `categoryGroups`     | `category_groups.csv`     | Category groups                                                                                                                                          |
| `categories`         | `categories.csv`          | Categories                                                                                                                                               |
| `transfers`          | `transfers.csv`           | Transfers (their two legs are in `transactions`)                                                                                                         |
| `transactions`       | `transactions.csv`        | Every ledger row, with `tags`, `transferId`, `payslipId`, `isPrivate` and `isMasked`                                                                     |
| `transactionSplits`  | `transaction_splits.csv`  | Split lines                                                                                                                                              |
| `payslips`           | `payslips.csv`            | Payslips (gross, net, deductions, transfer)                                                                                                              |
| `payslipLines`       | `payslip_lines.csv`       | Each payslip's gross and deduction lines (the transactions with that `payslipId`)                                                                        |
| `merchantRules`      | `merchant_rules.csv`      | Merchant rules, the bank defaults included                                                                                                               |
| `importBatches`      | `import_batches.csv`      | Bank imports with their counts and reconciliation balances (`archived` says whether the file is kept, never where)                                       |
| `importRows`         | `import_rows.csv`         | Each imported row's date, amount, resolution (and the importer's proposal), decision and the ledger rows it became or matched; never the bank file cells |
| `savingsGoals`       | `savings_goals.csv`       | Goals with `status` and `reachedAt`                                                                                                                      |
| `recurringItems`     | `recurring_items.csv`     | Recurring payments (cadence, amount, next date, status, source, edited fields)                                                                           |
| `monthlyInsights`    | `monthly_insights.csv`    | Monthly summaries: `headline`, `highlights`, `bodyMarkdown`                                                                                              |
| `llmUsage`           | `llm_usage.csv`           | LLM totals per month (household time zone) and purpose: calls, failed calls, tokens, cost in micro-dollars                                               |
| `ownershipTransfers` | `ownership_transfers.csv` | Ownership handovers (from, to, when)                                                                                                                     |

- Only the current household's rows, read page by page in id order with
  a keyset (memory stays flat; rows added or deleted mid-export never
  repeat nor vanish). No secrets: password hashes, tokens, invitation
  links and storage keys never leave.
- The privacy rule holds for the owner too: the partner's private
  transactions keep their amount but not their payee, notes, category,
  tags or split lines (`isMasked: true`, no `transactionSplits` rows, and
  their payslip line or import decision masked the same way). A payslip
  whose gross line is the partner's private row loses its memo, also where
  it was copied: its transfer's `memo` and the legs' `description`. The
  owner's own private rows are exported in full.
- CSV: a zip rather than one multi-section CSV, so each table keeps its own
  header and opens as a sheet of its own; the zip is written with
  node:zlib (no archive dependency). Each file is UTF-8 with a BOM, CRLF
  records, columns named like the JSON keys; lists of strings (tags) join
  with `; `, objects become JSON text; every text cell starting with
  `= + - @` (or tab/CR) is prefixed with `'` (numbers stay numbers).
  `ledger.csv` is the ledger as a spreadsheet: one row per posting (split
  lines expanded), names in the reader's locale, decimal amounts, the
  partner's private rows under "Private".

### Ledger and reports

`Transaction` = `{ id, accountId, kind (expense|income|transfer), date, bankDate,
amountCents (signed), currencyCode, payee, description, rawDescription,
categoryId, isSplit, splits[{ id, categoryId, amountCents, memo, sortOrder }],
transferId, paidByUserId (null = joint), status (pending|cleared), source
(manual|import|receipt|telegram), needsReview, cardSuffix, clientId, isPrivate,
isMasked, tags[], createdByUserId, updatedByUserId, createdAt, updatedAt }`.

| Name                          | Method and path                      | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

### Tags

Free labels on transactions (`tags[]`, e.g. a trip), up to 20 per row,
each trimmed and 1–40 characters, without NUL and not a lone `.` or `..`
(422 `regex`); matching is exact (case included). Split lines carry their
parent's tags; a transfer's tags sit on both legs (`transfers.store` /
`transfers.update`; an import that turns a tagged movement into a transfer
leg copies its tags to the other leg). Totals follow the month report's
rules (transfers never count as spending or income, refunds reduce their
category), and `setAsideCents` is what tagged transfers did to `savings`
accounts: money moved in counts, money moved out subtracts, savings to
savings nets to zero. The partner's private rows never reveal their tags: they
are left out of every tag (and a tag only they carry does not exist for the
reader). A tag is renamed (or merged into another) in one place with
`tags.update`, and added to or removed from a selection of rows with
`transactions.bulkTags`; neither touches the partner's private rows.

`TagTotals` = `{ tag, count (tagged movements: a split counts once, a
transfer once), expenseCents, incomeCents, netCents, setAsideCents,
firstDate, lastDate }` (dates of the first and last tagged movement in the
range, null when none).

### Payslips

A payout from an umbrella service (an account of kind `wallet`, any name):
the client pays the gross into the wallet, the service keeps the tax and its
fee, and transfers the net to the bank. A payslip records it as one income
row (the gross, category `salary`, payer = `userId`) and one expense row per
deduction in that account, every row carrying `payslipId`, and links the
wallet -> bank transfer of the net (one payslip per transfer). The rows are
ordinary ledger rows, so `reports.month` counts the gross as income and the
deductions as expenses with no special case. Invariant: `grossCents -
sum(deductions) = netCents = transfer amount`. Their amount, kind, account,
date and existence belong to the payslip: `PATCH`/`DELETE /transactions/:id`
answer 409 `E_PAYSLIP_LINE` when they would change them (category, payee,
notes, tags and privacy stay editable). There is no update: delete the
payslip and record it again. The linked transfer keeps its amount and source
account (`PATCH /transfers/:id` changing them answers 409 `E_PAYSLIP_LINE`;
date, memo and destination stay editable); deleting it keeps the payslip
with `transferId: null`.

`Payslip` = `{ id, accountId, userId (null = joint), date, grossCents,
netCents, deductionsCents, memo, transferId, transfer: { id, date,
amountCents, fromAccountId, toAccountId } | null, lines[{ transactionId, kind
(income|expense), categoryId, amountCents (signed: the gross positive first,
then the deductions negative), memo, isMasked }], clientId, createdByUserId,
createdAt, updatedAt }`. A line the partner made private keeps its amount but
not its category or memo (`isMasked: true`); when that line is the gross, the
payslip's `memo` is null too, and so is its copy on the transfer the payslip
created (`transfers.show` `memo`, both legs' `description` in
`transactions.index` / `transactions.show`, never matched by `q`). A memo
typed on the transfer afterwards is the transfer's own and shows again.

### Goals and insights

`Goal` = `{ id, name, targetCents, targetDate, startingCents,
monthlyContributionCents, accountId, userId (null = a goal of the household),
status (active|reached|archived), reachedAt, sortOrder, createdAt, updatedAt }`.

`GoalProjection` = `{ goalId, savedCents, targetCents, rateSource
(contribution|average|none), monthlyRateCents, remainingCents, monthsToGoal,
projectedDate, requiredMonthlyForTargetDate, onTrack, series[{ month,
projectedCents }], history[{ month, balanceCents }] }`. Month granularity from the current month in the
household time zone (point 0 = saved today, then one monthly rate per month,
at most 24 points): `projectedDate` is the first day of the month the target
is reached, a target date counts as its month, `onTrack` = projectedDate <=
targetDate. Saved = the account's cleared balance (else `startingCents`);
rate = `monthlyContributionCents` (an explicit 0 included), else the average
net (income - expense) of the last three full months (the current month and
the quiet months before any activity never count), else none. A rate that is
none or <= 0 leaves the goal open-ended (`monthsToGoal`, `projectedDate`,
`onTrack` null); reached = `remainingCents` 0, `monthsToGoal` 0; a past target
date gives `requiredMonthlyForTargetDate` null and `onTrack: false`.
`history` is what was saved at each month end, oldest first, the current
month last (the chart's actual line; `series` starts from its last point):
for a goal with an account, that account's cleared balance at the end of
each of the last 6 full months and of the current month (opening balance +
settled rows dated up to the month end, only rows after the opening balance
date when it is set; months that end before that date are left out); for a
goal without an account (contributions are not recorded), one point, the
current month at `startingCents`.

`Insight` = `{ month, locale, headline, bodyMarkdown, highlights[{ tone
(positive|neutral|warning), text }], model, generatedAt }`, one per household,
month and language (the request's locale). The model gets the month's totals,
the previous month's (null when it had no activity) and one line per category
(`{ slug, name, kind, amountCents, previousAmountCents }`, uncategorized as
slug `uncategorized`, names in that language), with every private purchase
counted in the totals but never as a line, the requester's own included: any
member reads the stored text.

### Bank imports and merchant rules

How the pipeline decides each row: [import-pipeline.md](import-pipeline.md).

`ImportBatch` = `{ id, accountId, status (staged|completed|cancelled), source
(nab_csv), fileName, archived, dateFrom, dateTo, counts: { rows, new,

`counts.rows` is every row of the file for the account, duplicates included
(listed as `duplicate` rows since 2026-10-16; older batches only count them).
`reconciliation`: the bank's balance on the newest row vs opening + ledger up
to `asOf` (projected while staged, measured on confirm); `balanced: false`
means movements before `missingBefore` are missing; `openingBalanceCents` is
set on the account's first import (derived from its oldest row).
`classifying` is true while a classify run holds the batch (a claim older
than 10 minutes belongs to a run that died and stops counting);
`classifiedAt` is when the last run ended (also when the model failed), or
null.

### Recurring payments

`RecurringItem` = `{ id, payee, merchantKey, cadence
(weekly|fortnightly|monthly|quarterly|yearly), amountCents (typical,
positive), amountTolerancePct, categoryId, accountId, paidByUserId (null =
joint), lastPaidDate, nextExpectedDate, status (active|paused|dismissed),
pausedByDetection, source (detected|manual), occurrences, createdAt,
updatedAt }`. One per household and `merchantKey` (the importer's
normalized payee key: the bank row's for an imported transaction, else the
payee's); `payee` is only its name and can be renamed. A payment belongs to
an item when its bank merchant key or its payee's own key is the item's key,
so an item typed as "Rent" matches the imported transfers the person named
"Rent". `pausedByDetection`: paused because its payments stopped, not by a
person.

Detection (`app/domain/recurring`) reads the household's expenses (whole
transactions, never transfers, income, refunds or a member's private
purchases) of the last twelve months, three years for yearly ones, grouped by
merchant key. Payments of the same day are one (their sum: both partners at
one gym). The typical amount is the median of the three latest payments;
only payments within 15% of it count (a one-off purchase or an old price is
left out). For each cadence the latest unbroken run decides: walking back
from the newest payment while each gap is one step or two (a missed payment)
in the cadence's range (weekly 6-8 days, fortnightly 13-15, monthly the same
day of the month give or take 3 days, quarterly and yearly give or take 7),
so a duplicate charge or a pause long ago does not hide what came after. The
run needs three payments, at least 75% of its gaps one step, steady amounts
(at least 80%, rounded down, of the merchant's payments within 50% of the typical amount are
within the tolerance, an old price before the run aside: weekly groceries of
varying amounts are not a bill) and a last payment no older than two steps
plus 31 days. The payer is whoever paid at least 75% of the run, else joint.
`nextExpectedDate` is the first step after the last payment on or after
today. Running it again is an idempotent upsert: a `dismissed` item is never
recreated; a pattern lands on the item with its merchant key, else on an
item typed by hand under one of its payee keys (never a second item for the
same bill); the observations (`occurrences`, `lastPaidDate`) refresh, and the
fields a person changed (any field sent to `PATCH`, `status` included) are
never overwritten; a next date a person set holds until a payment reaches
it. A detected item whose status no person chose is paused when its merchant has not been
paid for two steps plus 31 days (a cancelled subscription), and resumed when
its payments come back. It runs after every confirmed import too (best
effort, logged on failure).

`committed` of `reports.month`: for each active item, its due dates are
projected from `nextExpectedDate` with its cadence (weekly rent falls due
four or five times), on its day of the month for month-based cadences (a
bill due on the 31st stays on the 31st after a short month), never before an
item typed by hand starts. Its payments (amount within the item's tolerance;
a partner's private one never counts for the reader) are read from 60 days
before the month: each pays the due date it is closest to within the
cadence's window (weekly 3 days, fortnightly 7, monthly 14, quarterly 30,
yearly 60), then a payment left over pays the latest unpaid due date before
it within twice the window (paid late), so a late payment for last month
never pays this month's due date. `paidCents` and the `paid` lines are the item's payments dated in the
month. In the current month, every due date of the month nobody paid is
still due (`upcomingCents`), with `overdue: true` when its date is past (often
a bill whose bank export is not imported yet); a past month has nothing
still due, a future one every due date. `recurringCount` counts the active
and paused items (0 = nothing detected or added yet). With `paidByUserId`,
only that person's items and payments count. The client shows "Free after
bills" as `incomeCents - expenseCents - upcomingCents`, and "—" until the
month has income.

### Receipts and uploads

Receipt photos never pass through the API and nothing about a receipt is
stored. The flow:

1. `POST /uploads/presign` with what the client is about to upload: the
   server picks the key and signs a PUT for exactly that type and size.
2. The browser PUTs the photo (already reduced on the device) to `url` with
   `headers`, before `expiresAt`. Another type or size is refused by the
   bucket (403); the bucket allows the app origin through CORS
   (`node ace storage:configure`, see the runbook).
3. `POST /receipts/scan` with the `key`: the API reads the photo, reduces it
   again (≤ 1600 px, JPEG, metadata stripped), asks the vision model and
   deletes the photo whatever the outcome. A photo nobody scans expires from
   the bucket after one day. Each key scans once: retrying needs a new upload.
4. The person reviews the draft and saves it with `POST /transactions` and
   `source: 'receipt'` (`amountCents` from `totalCents`, `payee` from
   `merchant`, `categoryId`, or `splits` built from `items`).

`ReceiptDraft` = `{ merchant, date, totalCents, currencyCode, categoryId,
categorySlug, items: [{ description, amountCents, quantity }], confidence,
key }`. Amounts are cents as printed on the receipt (positive); any field but
`items`, `confidence` (0..1) and `key` is null when unreadable. `categorySlug`
is one of the household's visible categories (hidden ones are never offered)
and `categoryId` is that category's id.

### Push notifications

Web Push to the installed PWA (iOS 16.4+ only in the installed app). The
browser subscribes with `vapidPublicKey` from `GET /config` (Angular's
`SwPush.requestSubscription`) and hands the subscription over; the server
sends two kinds, from its scheduler (see the runbook): "summary ready" (on
the 1st, once per person and month) and the opt-in daily reminder (once per
local day after `reminderTime`, only when the person created nothing that
day). A subscription's endpoint is a capability URL: it goes in the body,
never in a path or query, and belongs to the person who registered it.

`NotificationSettings` (`@monkimoney/shared`) = `{ summaryReady (default
true), dailyReminder (default false), reminderTime ('HH:mm', household time
zone, default '20:00') }`, per person. `PushSubscription` = `{ id, endpoint,
userAgent, lastUsedAt, createdAt }` (never the keys).

A push message is what the Angular service worker shows: `{ notification:
{ title, body, tag, icon, badge, data: { url, onActionClick: { default: {
operation: 'focusLastFocusedOrOpen', url } } } } }`. A tap focuses the open
app, which routes to `data.url` (a path of the app) itself, or opens the app
there. Titles and bodies are in the recipient's language and never carry an
amount, a merchant or a name; the summary names its month only. Same `tag` =
the newer notification replaces the older one (`summary-YYYY-MM`,
`daily-reminder`).

# Architecture

monkimoney is one Docker image running one Node process: the AdonisJS 7 API,
which also serves the Angular 22 PWA from the same origin. Postgres 17 is the
only stateful dependency; files go to S3-compatible storage.

```
Phone (installed PWA) --HTTPS--> Cloudflare (proxy, WAF, cache rules)
                                   |
                                   v
                     Traefik (Dokploy, Cloudflare-only allowlist)
                                   |
                                   v
               monkimoney-web (Swarm service, 1 replica, start-first)
               node: AdonisJS API  +  Angular build in build/public
                     |                        |
                     v                        v
           monkimoney-db (Postgres 17,   Cloudflare R2 bucket (private): CSV
           internal network only)        originals; receipt photos PUT by the
                                         phone with a presigned URL, deleted
                                         after the scan
```

## Layout

API (`apps/api`): thin controllers (validate, call a service, transform),
services own use cases and DB transactions, `app/domain` is pure (no Lucid, no
I/O, no implicit `now`), repositories and scopes for tenancy, one concept per
file named after the concept. Web (`apps/web/src/app`): `core/` (API client,
session, i18n, theme, PWA), `domain/` (pure, no Angular), `shared/ui`,
`shared/charts`, `layouts/`, `features/<x>/{data-access,ui,feature}`.
Cloudflare Turnstile is the only external script the web loads:
`core/auth/turnstile.service.ts` appends it (explicit render, with
`ngsw-bypass` so the service worker never proxies it) when a login, sign-up
or forgot-password form opens and `GET /config` carries a
`turnstileSiteKey`; never from `index.html`, and without a site key nothing
is loaded or sent. E2E serves a stand-in for it (`e2e/support/turnstile.ts`).
Shared (`packages/shared`): wire types and pure helpers used by both sides,
compiled to `dist/` because Node does not load `.ts` from `node_modules`.

Monthly summary card (web): the Month view's insights slot leads with
`InsightSummaryCardComponent`, backed by a root `InsightsStore`
(`features/month/data-access`) that caches one summary per month and
language. Switching months reads the cache, a ledger change in the month
(`MonthStore.revisionOf`) drops its entry, and a change of the user's saved
locale (the language the API answers in) reads the other language. States:
_loading_ (skeleton); _missing_ (404: "Get your summary for {month}" with one
Generate button; nothing is generated without a tap); _generating_ (skeleton
and "Writing your summary"); _ready_ (headline, the body through
`domain/markdown-lite` rendered by templates only, never `innerHTML`,
highlights as a status icon plus a tone word, "Written by AI · Updated {time}",
and Regenerate (`force: true`) in an overflow sheet); quiet lines for 422
`month`/`noActivity` or `future`, 402 (AI limit reached) and 503 (summaries
off); and an error with Try again. A failed regenerate keeps the stored
summary and says why under it. The two deterministic insight cards stay below.

**Review before save (web).** Anything a machine proposes and a person
confirms (the bank import, the receipt scanner's lines) uses the same
pattern. `domain/import-row.ts` is the pure row state machine: a row's tone
(auto, doubtful, new, duplicate, transfer, ignored) from the API's proposal
plus the person's decision, the actions each tone allows, the optimistic
preview of a decision (`applyDecision`), the bulk changes, the confirm
payload (`decisionsFor`) and the reconciliation message. The screen's store
(`features/import/import-review.store.ts`) shows every decision at once,
`PATCH`es it, takes the API's answer and rolls back on refusal; confirm
sends `decisionsFor(rows)` again so a lost `PATCH` still lands, then
invalidates the months the file covers. The UI pieces live in
`shared/review/` and know nothing about imports (see its README):
`ReviewList` (leading checkbox, selection, progressive rendering; the row is
the consumer's template), `RowTriage` (the triage sheet's frame and slots)
and `BulkBar` (the selection's actions). The CSV goes up through
`core/api/upload.service.ts` (XHR: real progress, abort, the same CSRF header
as Tuyau), since fetch cannot report upload progress.

**Receipt scanner (web).** `/scan` (camera with `capture="environment"`,
or the photo library; entry points in the quick add header and the More
menu) never uploads the photo as taken: `core/platform/image-optimizer.ts`
decodes it with `createImageBitmap` (EXIF rotation applied), or with an
`<img>` from a `blob:` URL where that refuses it (HEIC on Safari), draws it at
most 1600 px on its longest side on a canvas (every metadata field is
dropped) and writes WebP 0.8, or JPEG 0.82 where the browser cannot write
WebP (the math is pure in `domain/image-optimizer.ts`); a photo neither
decoder opens is refused naming its format ("This browser cannot open HEIC
photos"). The store (`features/scan/scan.store.ts`) checks the reduced photo
against the upload limits shared with the API (`@monkimoney/shared`
`receipts.ts`: JPEG, PNG or WebP, at most 10 MB), asks
`POST /uploads/presign` for a URL sized to that blob, PUTs it straight to
the bucket with
`UploadService.putToUrl` (only the signed headers, no cookies or CSRF
token, real progress; a 403 from an expired URL gets one fresh presign)
and calls `POST /receipts/scan` with the key. Scanning needs the network:
offline is said, never queued, and "Try again" uploads under a new key
(each key scans once). The draft opens in the shared `TransactionForm`
(merchant, date, total, offered category, last used account, you as the
payer) with a confidence hint, and "Split by lines" lists the printed lines
in `ReviewList` with `BulkBar` (merge, drop, category; the last line takes
the difference to the total, `domain/receipt-draft.ts`). A receipt whose
`currencyCode` differs from the household's opens with a warning: saving
waits for "Continue" (the amounts are saved as typed, in the household's
currency, never converted) and "Cancel" drops the draft. Saving posts
`POST /transactions` with `source: 'receipt'` and one client id per review.
The photo is never persisted: the original's preview is a `blob:` URL
revoked once the draft is back, and the reduced copy stays in memory as
another one ("Show photo", folded above the fields) only while the review
is open; both go on cancel, on discard, with a new photo and when the screen
goes away.

## Offline outbox (web)

Quick add never loses an entry. Every create carries a `clientId` (uuid)
that makes `POST /transactions/quick` and `POST /transfers` idempotent, so
the web can resend freely. When the device is offline (`navigator.onLine`
false) or the save fails for lack of network, a 5xx or a 429, quick add
puts the API body in the **outbox** with the client id it already tried
and clears the form ("Saved offline · will sync"); a 422 stays under the
fields and queues nothing. The rules are pure (`domain/outbox.ts`: FIFO,
`pending | syncing | failed`, retryable failures count attempts with a
1 s → 60 s backoff, a 4xx becomes `failed` with the API's message, a
versioned serialization that drops corrupt entries instead of throwing);
`core/outbox/outbox.store.ts` owns the state. It is persisted per person
in localStorage (`outbox:<userId>`, written synchronously before the toast)
and synced one entry at a time on sign-in, on the `online` event, when the
app returns to the foreground, after every successful quick-add save and on
the backoff timer, never while signed out. Open tabs share that copy: every
change starts from it (`reconcile`: the device copy wins, an entry this tab
is sending stays `syncing`) and the `storage` event reloads it, so neither
tab drops the other's newest entry; both may send the same entry, which the
client id makes harmless. When localStorage refuses the write (quota,
private mode) the outbox works from memory until the app closes, the pill
says "not persisted" and quick add's toast says to keep the app open. A
synced entry invalidates its month (`MonthStore`); a 409 counts as synced.
"Undo" on the "Saved offline" toast drops the queued entry, or deletes the
row it became once synced (the store remembers the created ids for the
session). An explicit logout deletes the outbox from the device
(`SessionStore.onLogout`), so the More tab's "Log out" goes through
`layouts/outbox/safe-logout.ts`: while entries wait it asks first ("N
movements are waiting to sync and will be lost": Sync now, which logs out
once nothing is left, Log out anyway, Cancel). An expired session keeps the
outbox for the next login of the same person. The sync pill above the tab
bar is the only place that shows what is not on the server yet (lists and
the Month view never merge queued entries): it opens a sheet to retry, edit
(quick add with `?outbox=<id>`, which holds the entry and replaces it
keeping its client id) or discard. Quick add's own rankings (category
tiles, payees, routes) do count queued entries (`queuedAsRecent`). The
service worker never caches `/api`; the outbox, not the SW, is what makes
writes survive offline.

## Build info

`.app-version` (from the root `package.json`) and `.git-sha` (from the
`gitsha` stage, or the `GIT_SHA` build arg) are written next to the compiled
API (`/app/apps/api/build` in the image). Non-empty `APP_VERSION` / `GIT_SHA`
env vars override them; without either the API reports `dev` / `unknown`.
